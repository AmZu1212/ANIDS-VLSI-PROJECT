# ANIDS C++ Model Documentation

This document describes the ANIDS C++ model and the comparison flow located under `ANIDS Model`. The model is used to check the RTL implementation by running the same programmed test case through two paths:

1. The C++ integer model in `ANIDS Model/cpp/anids_model.cpp`.
2. The RTL design through `ANIDS Model/rtl/anids_model_compare_tb.sv`.

The outputs from both paths are compared by `ANIDS Model/run_test`. The comparison is exact: for each input vector, the C++ result and RTL result must have the same vector index, loss value, and anomaly bit.

The term "golden model" is intentionally avoided in the project. This is a C++ comparison model for the ANIDS datapath. It is useful because it gives a fast, readable software implementation of the same fixed-point behavior expected from the RTL.

## How The Model Flow Is Organized

The ANIDS model flow is built around three main pieces:

| Piece | File | Role |
| --- | --- | --- |
| C++ model | `ANIDS Model/cpp/anids_model.cpp` | Computes the expected loss/anomaly result using an integer model of the datapath. |
| Python runner | `ANIDS Model/run_test` | Builds the C++ model, generates the RTL program file, runs both C++ and RTL, and compares outputs. |
| RTL comparison testbench | `ANIDS Model/rtl/anids_model_compare_tb.sv` | Runs the real RTL top-level design using the same test configuration and prints RTL results. |

The flow is:

```text
Test folder
  weights.txt
  threshold.txt
  loss_function.txt
  inputs.txt
        |
        v
Python runner: run_test
        |
        +--> generates outputs/program.prog for RTL programming
        |
        +--> compiles and runs C++ model
        |       |
        |       v
        |     outputs/cpp.out
        |
        +--> compiles and runs RTL comparison testbench
                |
                v
              outputs/verilog.out
        |
        v
Compare cpp.out vs verilog.out
        |
        v
outputs/diff.out
```

This structure keeps the test definition independent of either implementation. The same `weights.txt`, `threshold.txt`, `loss_function.txt`, and `inputs.txt` files drive both the C++ model and the RTL simulation.

## Purpose Of The Model

The C++ model mirrors the ANIDS datapath at the integer level. It is not written as a high-level neural network model using floating point. Instead, it uses the same compact integer representation used by the hardware:

| Quantity | Representation |
| --- | --- |
| Weights | Signed 8-bit Q0.7 codes. |
| Biases | Signed 8-bit Q0.7 codes. |
| LUT values | Signed 8-bit Q0.7 codes. |
| Threshold | Signed 8-bit Q0.7 code. |
| Input vector | 128 raw feature bits. |
| Hidden results | Signed 8-bit values after ReLU clamp. |
| Output results | Signed 8-bit values. |
| Loss | Signed 8-bit result after accumulation/truncation. |

A Q0.7 value is stored as an integer code. For example:

```text
64   represents +0.5
127  represents the largest positive 8-bit Q0.7 code
-128 represents -1.0
0    represents zero
```

The model keeps these values as integers and explicitly applies two's-complement wrapping, truncation, signed interpretation, and saturation where the RTL does the same thing.

## C++ Model Structure

The main C++ file is:

```text
ANIDS Model/cpp/anids_model.cpp
```

The important constants at the top of the file mirror the RTL configuration:

| Constant | Value | Meaning |
| --- | --- | --- |
| `dmaVectorWidth` | `128` | Input vector width in bits. |
| `hiddenNeuronCount` | `64` | Number of hidden-layer neurons. |
| `outputNeuronCount` | `128` | Number of output-layer neurons. |
| `q07Width` | `8` | Width of Q0.7 values. |
| `hiddenAccWidth` | `15` | Hidden-layer accumulator width. |
| `outputAccWidth` | `15` | Output-layer accumulator width. |
| `lossAccWidth` | `15` | Loss accumulator width. |
| `lutAddrWidth` | `8` | Lookup table address width. |

The model state is stored in the `Config` structure:

| Field | Purpose |
| --- | --- |
| `n` | Active vector size. Default is `128`. |
| `threshold` | Anomaly threshold. |
| `hiddenWeights` | 64 by 128 hidden-weight matrix. |
| `hiddenBiases` | 64 hidden biases. |
| `outputWeights` | 128 by 64 output-weight matrix. |
| `outputBiases` | 128 output biases. |
| `functionLut` | 256-entry lookup/function table. |

Unspecified weights, biases, and LUT entries default to zero because the arrays are initialized to zero.

The input vector is stored as two 64-bit words in `InputVector`:

```text
low  = bits 63:0
high = bits 127:64
```

The helper `GetInputBit()` selects the correct bit from either half.

## Integer Helper Functions

The C++ model includes helper functions to reproduce RTL-style fixed-width behavior:

| Function | Purpose |
| --- | --- |
| `MaskBits(bits)` | Creates a bit mask for a fixed width. |
| `ToSigned(value, bits)` | Interprets a fixed-width value as signed two's complement. |
| `WrapSigned(value, bits)` | Wraps a value to a signed fixed width. |
| `WrapUnsigned(value, bits)` | Wraps a value to an unsigned fixed width. |
| `TruncSliceSigned(value, inBits, msb, width)` | Models a SystemVerilog part-select followed by signed interpretation. |
| `SaturatingAddQ07(lhs, rhs)` | Adds two 8-bit Q0.7 codes and saturates to `[-128, 127]`. |
| `ReluQ07(value)` | Applies ReLU by clamping negative values to zero. |

These helpers are important because ordinary C++ integer arithmetic does not automatically behave like fixed-width RTL arithmetic. Without explicit wrapping and truncation, the C++ model could accidentally use wider intermediate values and disagree with the hardware.

## Input Layer Behavior

The model processes the input vector in 2-bit feature pairs. The helper function:

```text
InputLayerPair(featureVector, counter)
```

extracts:

```text
bit 2*counter
bit 2*counter + 1
```

and returns the pair as:

```text
pair[0] = lower feature bit
pair[1] = upper feature bit
```

For `N = 128`, there are 64 feature-pair cycles. This matches the pipeline structure of the RTL, where the 128-bit vector is consumed two feature bits at a time.

Inside the hidden and loss calculations, the model calls `InputLayerPair(featureVector, counter - 1)`. This mirrors the registered timing of the RTL pipeline, where the useful feature pair is delayed relative to the counter value. This detail is important for bit-accurate comparison.

## Hidden Layer Model

The hidden layer is computed by:

```text
HiddenNeuronResult(featureVector, weights, bias, n)
```

This function models one hidden neuron. The full hidden layer is produced by calling this function for all 64 hidden neurons.

For each feature-pair cycle, the model:

1. Selects the current 2-bit feature pair.
2. Gates each of the two weights based on whether the corresponding feature bit is `1`.
3. Adds the two active weights.
4. Wraps the pair sum to 9 bits.
5. Accumulates the pair sum into a 15-bit accumulator.

At the final pair for the selected `N`, the accumulated value is truncated down to an 8-bit signed Q0.7 code. The hidden bias is then added with saturation. Finally, ReLU is applied so negative hidden values become zero.

The hidden result therefore follows the same broad sequence as the RTL:

```text
feature gating -> accumulation -> truncation -> bias add -> saturation -> ReLU
```

## Output Layer Model

The output layer is computed by:

```text
OutputNeuronResult(hiddenResults, weights, bias, n)
```

This function models one output neuron. The full output layer is produced by calling this function for all 128 output neurons.

For each counter cycle, the model:

1. Selects one hidden-layer result.
2. Multiplies it by the corresponding output weight.
3. Wraps the full product to 16 bits.
4. Selects the Q0.7 product slice.
5. Accumulates the sliced product into a 15-bit accumulator.

At the final step, the accumulator is truncated to 8 bits and the output bias is added with Q0.7 saturation. The output layer does not apply ReLU at the end; the result remains signed.

This mirrors the RTL output-layer behavior where hidden activations feed the output neurons through signed multiply-accumulate logic.

## Lookup Mapping

The C++ model uses:

```text
MemoryMapper(inValue)
```

to convert a signed 8-bit output result into an 8-bit LUT address.

The mapping flips the sign bit and keeps the lower seven bits:

```text
lut_addr = {~sign_bit, value[6:0]}
```

This matches the RTL `memory_mapper`. The purpose is to map signed output-layer values into the unsigned address space of the function LUT.

After mapping, the model reads:

```text
config.functionLut[mapped_address]
```

for each output result used by the loss function.

## Loss Function Model

The loss function is computed by:

```text
LossResult(featureVector, outputResults, config)
```

For each feature pair, the model:

1. Reads the original input feature bits.
2. Selects the two corresponding output-layer results.
3. Maps each output result into a LUT address.
4. Reads the two function values from the LUT.
5. Computes absolute differences between the input bits and function values.
6. Adds the pair loss into a 15-bit accumulator.

The pair loss is:

```text
abs(x0 - f0) + abs(x1 - f1)
```

At the final pair, the accumulated loss is truncated to an 8-bit signed value. This final loss is compared against the configured threshold:

```text
anomaly = loss > threshold
```

The comparison is strictly greater-than. If the loss equals the threshold, the model reports non-anomaly.

## Full Model Flow

The top-level function for one input vector is:

```text
RunModel(featureVector, config)
```

The flow is:

```text
Input vector
   |
   v
Hidden layer: 64 hidden neuron results
   |
   v
Output layer: 128 output neuron results
   |
   v
Lookup + loss function
   |
   v
Threshold comparison
   |
   v
RESULT vector=<index> loss=<loss> anomaly=<0_or_1>
```

The C++ executable runs this flow for every vector listed in `inputs.txt`.

## Test Folder Format

Each model test lives under:

```text
ANIDS Model/tests/<test_name>/
```

Each test folder contains:

| File | Purpose |
| --- | --- |
| `weights.txt` | Defines `N`, hidden weights/biases, and output weights/biases. |
| `threshold.txt` | Defines the anomaly threshold. |
| `loss_function.txt` | Defines LUT/function table entries. |
| `inputs.txt` | Defines one or more 128-bit DMA vectors. |

After running the test, the runner creates:

| Generated File | Purpose |
| --- | --- |
| `outputs/program.prog` | APB-style program generated from the test files. |
| `outputs/cpp.out` | C++ model result lines. |
| `outputs/verilog.out` | RTL result lines. |
| `outputs/diff.out` | PASS/FAIL comparison result. |

A complete test folder has this structure:

```text
ANIDS Model/tests/<test_name>/
  weights.txt
  threshold.txt
  loss_function.txt
  inputs.txt
  outputs/
    program.prog
    cpp.out
    verilog.out
    diff.out
```

The `outputs` folder is generated by the runner. The four text files at the top of the test folder are the actual test source files.

The test source files are intentionally simple text files. This makes it easy to create directed tests by hand and also easy to generate larger tests from scripts. Blank lines are allowed. Comments are allowed using `#`; anything after `#` on a line is ignored.

Example minimal test source layout:

```text
weights.txt:
  N 128
  HLW 0 0 64
  HLB 0 1
  OLW 0 0 64
  OLB 0 0

threshold.txt:
  60

loss_function.txt:
  LUT 128 0
  LUT 129 1

inputs.txt:
  00000000000000000000000000000000
```

In this example, only a few weights are programmed. Every unspecified hidden weight, hidden bias, output weight, output bias, and LUT entry defaults to zero.

## `weights.txt`

The weights file supports the following directives:

```text
N <value>
HLW <hidden_neuron> <feature_index> <value>
HLB <hidden_neuron> <value>
OLW <output_neuron> <hidden_index> <value>
OLB <output_neuron> <value>
```

The directives mean:

| Directive | Meaning |
| --- | --- |
| `N` | Active vector size. The current tests use `128`. |
| `HLW` | One hidden-layer weight. |
| `HLB` | One hidden-layer bias. |
| `OLW` | One output-layer weight. |
| `OLB` | One output-layer bias. |

Values may be decimal or hex:

```text
64
-64
0x40
0xC0
```

Weights and biases are interpreted as signed 8-bit values. A value such as `-1` is interpreted as signed `-1`, while a value such as `0xFF` is also interpreted as signed `-1`.

Unspecified values are zero. This is useful for directed tests where only a small number of weights are needed.

## `threshold.txt`

The threshold file contains one value:

```text
60
```

The threshold is interpreted as a signed 8-bit value. The final anomaly decision is:

```text
loss > threshold
```

## `loss_function.txt`

The loss function file programs the LUT used by the lookup layer. It supports two equivalent formats:

```text
LUT <address> <value>
```

or:

```text
<address> <value>
```

Each value is interpreted as signed 8-bit data. The included tests use LUT values derived from:

```text
Documentation/sigmoid_lut_table.csv
```

## `inputs.txt`

The inputs file contains one 128-bit DMA vector per line, written as hexadecimal text:

```text
00000000000000000000000000000000
FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
```

If multiple vectors are listed, the C++ model processes all of them in order. The RTL comparison bench also streams all of them into `anids_top` and collects one result per vector.

## Generated APB Program

The Python runner converts the test files into:

```text
outputs/program.prog
```

This file contains one APB-style write per line:

```text
<address_hex> <data_hex>
```

The generated address map follows the design register map:

| Region | Address Calculation |
| --- | --- |
| `START_REG` | `0` |
| `N_REG` | `1` |
| `THRESHOLD_REG` | `2` |
| `LUT_ADDR` | `4` |
| `LUT_DATA` | `5` |
| `LUT_CTRL` | `6` |
| Hidden weights | `HL_WEIGHT_BASE + neuron * 128 + feature` |
| Hidden biases | `HL_BIAS_BASE + neuron` |
| Output weights | `OL_WEIGHT_BASE + neuron * 64 + hidden_index` |
| Output biases | `OL_BIAS_BASE + neuron` |

For each LUT entry, the runner emits a four-write sequence:

```text
LUT_ADDR = address
LUT_DATA = value
LUT_CTRL = 1
LUT_CTRL = 0
```

This follows the RTL programming convention for writing the function LUT.

## `run_test` Flow

The main runner is:

```text
ANIDS Model/run_test
```

It is a Python script. From the `ANIDS Model` folder, it can be run as:

```text
python .\run_test sparse_directed_signed
```

or:

```text
python .\run_test .\tests\sparse_directed_signed
```

The runner performs these steps:

1. Resolves the requested test folder.
2. Checks that `weights.txt`, `threshold.txt`, `loss_function.txt`, and `inputs.txt` exist.
3. Generates `outputs/program.prog`.
4. Compiles the C++ model using `g++` or `clang++`.
5. Runs the C++ model and writes `outputs/cpp.out`.
6. Compiles the RTL comparison testbench with `iverilog`.
7. Runs the RTL simulation with `vvp`.
8. Filters RTL output down to `RESULT` lines and writes `outputs/verilog.out`.
9. Parses both output files.
10. Writes `outputs/diff.out`.
11. Prints `PASS` if the parsed C++ and RTL result tuples match exactly.

The expected result line format is:

```text
RESULT vector=<index> loss=<signed_loss> anomaly=<0_or_1>
```

The comparison regex in the runner only accepts this format, which keeps the output parsing strict.

### Python Runner Responsibilities

The Python runner is the coordinator for the whole comparison. It does not implement the ANIDS datapath itself. Instead, it prepares the files and commands needed to run both implementations in the same way.

Its main responsibilities are:

| Responsibility | What The Runner Does |
| --- | --- |
| Test discovery | Accepts either a test name like `sparse_directed_signed` or a direct path to a test folder. |
| Input validation | Checks that all required files exist before running simulation. |
| Program generation | Converts the human-readable test files into `outputs/program.prog`. |
| C++ compilation | Builds `anids_model.cpp` into `ANIDS Model/build/anids_model.exe` or `anids_model`. |
| C++ execution | Runs the compiled model with the four test input files. |
| RTL compilation | Uses `iverilog -g2012` to compile `anids_model_compare_tb.sv` with all RTL sources. |
| RTL execution | Uses `vvp` and passes `+PROGRAM` and `+INPUTS` plusargs to the testbench. |
| Output filtering | Keeps only RTL lines matching the `RESULT vector=...` format. |
| Result comparison | Parses `cpp.out` and `verilog.out` into tuples and compares them exactly. |
| Reporting | Writes `diff.out` and prints `PASS` or `FAIL`. |

The runner generates the APB program using the same register-map constants as the RTL design. For example, a hidden weight directive:

```text
HLW 3 17 -64
```

is converted into an APB-style write at:

```text
HL_WEIGHT_BASE + 3 * 128 + 17
```

with the data value stored as an 8-bit two's-complement value. This is how the readable test format becomes the actual programmed RTL state.

The runner also handles LUT programming. Each LUT line is expanded into the required write sequence to `LUT_ADDR`, `LUT_DATA`, and `LUT_CTRL`. This means the test author only writes the logical LUT contents, while the runner handles the programming protocol.

### Runner Output Files

For every test, the runner writes the following files:

| File | Meaning |
| --- | --- |
| `program.prog` | The generated APB write program used by the RTL comparison bench. |
| `cpp.out` | Raw C++ model result lines. |
| `verilog.out` | Filtered RTL result lines. |
| `diff.out` | Comparison result and mismatch details if the test fails. |

For a passing test, `diff.out` contains:

```text
PASS: cpp.out and verilog.out match
```

For a failing test, `diff.out` includes both result streams so the first mismatch can be inspected directly.

## RTL Comparison Bench

The RTL side of the comparison is:

```text
ANIDS Model/rtl/anids_model_compare_tb.sv
```

This bench instantiates the full `anids_top`. It receives two plusargs from the runner:

```text
+PROGRAM=<program.prog>
+INPUTS=<inputs.txt>
```

The RTL bench then:

1. Resets the design.
2. Loads the generated program.
3. Loads all input vectors.
4. Starts the core.
5. Streams the input vectors through the DMA handshake.
6. Collects one result per vector.
7. Prints the same `RESULT vector=... loss=... anomaly=...` format as the C++ model.

For speed, the comparison bench programs much of the model state through hierarchical/backdoor writes instead of using APB for every weight. It still uses the real top-level design and the real DMA streaming path for execution. LUT programming is handled carefully by shadowing the LUT address/data registers and writing both LUT banks when `LUT_CTRL` is asserted.

The bench collects results on `core_done` and reads:

```text
dut.core_loss_result
dut.core_outlier_pulse
```

These are printed as the RTL comparison result.

### RTL Testbench Operation

The comparison testbench is designed to make the RTL produce the same output format as the C++ model. It does not decide pass/fail by itself. Its job is to run the RTL and print deterministic `RESULT` lines.

At startup, the bench requires two plusargs:

```text
+PROGRAM=<path_to_program.prog>
+INPUTS=<path_to_inputs.txt>
```

If either plusarg is missing, the testbench stops with `$fatal`. This prevents accidental runs with an unprogrammed design or missing input vectors.

The bench execution sequence is:

1. Initialize all APB and DMA signals.
2. Apply reset to `anids_top`.
3. Read `program.prog`.
4. Program the register file and LUT contents.
5. Read all input vectors from `inputs.txt`.
6. Write `START_REG = 1` through the APB task.
7. Stream the vectors into the DUT using the DMA valid/ack handshake.
8. Wait for one `core_done` pulse per input vector.
9. Print one result line per completed vector.
10. Write `START_REG = 0` after all vectors complete.

The result print is:

```text
RESULT vector=<idx> loss=<dut.core_loss_result> anomaly=<dut.core_outlier_pulse>
```

This is intentionally the same format printed by the C++ executable. Because the two outputs have the same structure, the Python runner can compare them directly.

### Programming Method Used By The Bench

The comparison bench uses a mixed programming approach:

| State | Programming Method |
| --- | --- |
| `START_REG` during run/stop | APB task. |
| Main register file contents from `program.prog` | Hierarchical/backdoor writes for speed. |
| LUT contents from `program.prog` | Hierarchical/backdoor writes into both LUT memories. |
| DMA input vectors | Real DMA handshake through `dma_valid`, `dma_ack`, and `dma_data`. |

The backdoor programming is used because full-capacity tests can contain thousands of weight writes. Programming every weight over APB would make the comparison simulation much slower. The actual datapath execution still happens through the real RTL design after the state has been loaded.

For LUT writes, the bench watches the generated writes to `LUT_ADDR`, `LUT_DATA`, and `LUT_CTRL`. When `LUT_CTRL` is written with bit `0` set, the bench writes the shadowed LUT address/data into both lookup-layer LUT banks:

```text
function_lut_0
function_lut_1
```

This matches the design requirement that both lookup lanes see the same programmed function table.

### Streaming And Result Collection

The bench stores up to 1024 input vectors from `inputs.txt`. During execution, it sends each vector only when the DUT asserts `dma_ack`. The handshake sequence is:

```text
wait for dma_ack == 1
drive dma_data
assert dma_valid for one cycle
drop dma_valid
wait for dma_ack == 0
```

In parallel, the bench waits for `core_done` once per expected vector. When `core_done` rises, it samples the final loss and outlier pulse from the core and prints the result line. This allows multi-vector tests such as `random_full_model_mixed` to check steady-state RTL behavior against the C++ model across many inputs.

## Included Tests

### `sparse_directed_signed`

Path:

```text
ANIDS Model/tests/sparse_directed_signed
```

This is a small directed test with sparse nonzero weights. Only selected hidden and output weights are programmed, while the rest remain zero. The purpose is to make the numeric behavior easier to inspect while still exercising signed values, feature gating, ReLU behavior, output accumulation, LUT mapping, loss calculation, and thresholding.

This test is useful for debugging because a small number of programmed weights makes it easier to trace which inputs affect the final loss.

### `dense_directed_signed`

Path:

```text
ANIDS Model/tests/dense_directed_signed
```

This is a directed test with a denser set of programmed weights than `sparse_directed_signed`. It increases the amount of active arithmetic in the hidden and output stages while still remaining small enough to inspect manually.

The test exercises stronger accumulated values, signed weights, bias effects, and saturation paths more heavily than the sparse case. It is intended to catch indexing and arithmetic errors that may not appear when only a few weights are nonzero.

### `random_full_model_mixed`

Path:

```text
ANIDS Model/tests/random_full_model_mixed
```

This is the largest included model test. It explicitly programs the full model capacity:

```text
8192 hidden weights
64 hidden biases
8192 output weights
128 output biases
```

The input file contains multiple streamed vectors. This test checks that the C++ model and RTL continue to match over a larger, more realistic configuration with many weights and repeated result generation.

This case is important because it provides broad coverage of the full address map and the steady-state streaming behavior of the RTL comparison bench.

### `zero_model_zeros`

Path:

```text
ANIDS Model/tests/zero_model_zeros
```

Despite the historical name, this test no longer uses a zero-weight model. It now loads a full-capacity model and drives an all-zero input vector. This makes the test meaningful because the result depends on the programmed weights and not only on reset-default zero state.

The current observed result after the recent update is:

```text
RESULT vector=0 loss=63 anomaly=0
```

This checks the all-zero input pattern against a fully programmed model and a high threshold.

### `zero_model_ones`

Path:

```text
ANIDS Model/tests/zero_model_ones
```

This test also now loads a full-capacity model, but drives an all-ones input vector. It complements `zero_model_zeros` by checking the opposite input pattern while using the same style of full model programming.

The current observed result after the recent update is:

```text
RESULT vector=0 loss=62 anomaly=1
```

This checks the all-ones input pattern against a fully programmed model and a lower threshold.

## What A Passing Test Means

When `run_test` prints:

```text
PASS
```

it means:

1. The C++ model compiled successfully.
2. The C++ model ran successfully.
3. The RTL comparison testbench compiled successfully.
4. The RTL simulation ran successfully.
5. The C++ output and RTL output matched exactly for every vector.

A passing test does not prove that the mathematical algorithm is ideal. It proves that, for the tested configuration, the C++ model and RTL implementation agree on the implemented integer behavior.

## What A Failing Test Means

When a test fails, the first file to inspect is:

```text
ANIDS Model/tests/<test_name>/outputs/diff.out
```

If the C++ and RTL outputs differ, the diff file includes both sides. For example:

```text
FAIL: cpp.out and verilog.out differ

CPP:
RESULT vector=0 loss=...

VERILOG:
RESULT vector=0 loss=...
```

Useful debug files are:

| File | Use |
| --- | --- |
| `outputs/program.prog` | Confirms the APB program generated from the test inputs. |
| `outputs/cpp.out` | Shows C++ model results. |
| `outputs/verilog.out` | Shows filtered RTL results. |
| `ANIDS Model/build/anids_model.exe` | Confirms that the C++ executable was produced. |
| `outputs/sim_anids_model_compare_tb.out` | Compiled RTL simulation output under the repo-level `outputs` folder. |

If the failure occurs before comparison, the terminal error usually indicates the problem: missing compiler, missing `iverilog`, missing `vvp`, malformed test file, invalid directive, or RTL simulation failure.

## Model Coverage

The model comparison flow covers:

| Area | Covered By |
| --- | --- |
| Hidden weights and biases | `HLW`, `HLB`, hidden-layer C++ path, RTL hidden layer. |
| Output weights and biases | `OLW`, `OLB`, output-layer C++ path, RTL output layer. |
| Signed Q0.7 handling | C++ signed helpers and RTL fixed-width arithmetic. |
| Feature-pair processing | Input parsing, pair selection, hidden/loss loops. |
| LUT mapping | `MemoryMapper` and RTL lookup address mapping. |
| Loss accumulation | C++ `LossResult` and RTL loss function. |
| Thresholding | C++ anomaly comparison and RTL outlier pulse. |
| Streaming vectors | Multi-vector input files and RTL DMA streaming. |
| Full-model programming | `random_full_model_mixed`, `zero_model_zeros`, `zero_model_ones`. |

This makes the model flow a strong end-to-end regression check for the implemented ANIDS datapath.

## Relationship To Other Verification

The project has several verification layers:

| Verification Layer | Location | Purpose |
| --- | --- | --- |
| RTL unit/integration testbenches | `ANIDS/tb` | Directly test individual blocks and integrated RTL subsystems. |
| C++ model comparison flow | `ANIDS Model` | Compare the C++ integer datapath model against full RTL execution. |

The C++ model flow is not a replacement for unit tests. The unit tests are still useful because they isolate failures in individual RTL blocks. The model flow is valuable because it checks that the full programmed datapath produces the same final loss/anomaly results as an independent integer implementation.

## Practical Notes

1. Keep test files ASCII. The parser expects simple whitespace-separated text.
2. Use comments with `#` when needed. Both the C++ model and Python runner ignore text after `#`.
3. Remember that unspecified weights and biases default to zero.
4. Use decimal values for readability unless a hex representation is specifically helpful.
5. When changing RTL arithmetic, update the C++ helper behavior if the fixed-width behavior changes.
6. When changing register-map constants, update both the RTL defines and the address constants used by `run_test`.
7. When adding a new model test, include all four required files: `weights.txt`, `threshold.txt`, `loss_function.txt`, and `inputs.txt`.
